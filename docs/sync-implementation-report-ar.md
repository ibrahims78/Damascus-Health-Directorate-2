# تقرير تنفيذ المزامنة الكاملة (Capture → Transport → Materialization)

**المشروع:** Damascus-Health-Directorate (مستودعات مديرية صحة دمشق)
**التاريخ:** 2026-08-27
**الحالة:** ✅ مكتمل ومُختبَر بنجاح (44/44 اختباراً)

---

## 1. الخلاصة التنفيذية

تم إكمال دورة المزامنة من طرف إلى طرف بين نسختين من النظام (نسختان سطح مكتب / ويندوز، وأساس جاهز لأندرويد):

- **التقاط (Capture):** كل عملية كتابة تُسجَّل تلقائياً في سجل تغييرات موحّد مع لقطة كاملة للصف.
- **النقل (Transport):** قناتان — تبادل شبكي مباشر، أو حزم ملفات `.dme-sync` مشفّرة قابلة للنقل اليدوي.
- **التطبيق المادي (Materialization):** مُطبِّق يعيد بناء البيانات على الجهة المستقبلة بترتيب آمن، مع تعارضات تُسجَّل وتُسوَّى بدل أن تُسقط الحزمة.

النتيجة: نسختان من النظام تتقاربان (تتطابق بياناتهما) سواء عبر الشبكة أو عبر ملف يُنقل باليد، دون فقدان أو ازدواج، مع قدرة كاملة على تتبّع التعارضات وحلّها.

## 2. كيف تعمل المزامنة (المعمارية)

### 2.1 التقاط التغييرات (Capture)

كل تعديل في البيانات التجارية يمر عبر `recordLocalChange` (في `sync-service.ts`) الذي يسجّل في `sync_change_log`:

| الحقل | الوظيفة |
|---|---|
| `changeId` | معرّف فريد للتغيير نفسه (لإزالة الازدواجية عند إعادة التسليم) |
| `operationId` | معرّف العملية الأصلية (لاكتشاف تعديلين على نفس العملية) |
| `entityType` / `entityGlobalId` | نوع الكيان ومعرّفه العمومي (مستقل عن معرّف كل نسخة المحلي) |
| `changeType` | إنشاء / تعديل / حذف |
| `payload` | **لقطة كاملة للصف بعد الكتابة** — فيمكن للمستقبِل استرجاع صف ناقص بمجرد الإدراج |
| `originNodeId` / `originSequence` | هوية العقدة المصدر ورقمها التسلسلي (لبناء المتجهات والتفاضل) |

النقاط المغطاة بالالتقاط:
- الأصناف (categories): إنشاء/تعديل/حذف بلقطات كاملة.
- المواد (items): إنشاء/تعديل/حذف مع `categoryGlobalId`، ودُفعة الافتتاح تُسجَّل كتغيير `inventory_batch` مستقل.
- المعدات (equipment): إنشاء/تعديل/حذف.
- حركات المخزون (transactions): عبر `buildMovementSyncPayload` تُبنى **حزمة** تتضمن:
  - صف الحركة نفسه (مع `itemGlobalId` / `equipmentGlobalId` ورقم السند وتاريخه).
  - تأثير المخزون: لقطة المادة بعد الحركة (فيُتقارب الرصيد).
  - حالة FEFO: كل دفعات المادة مع أرصدتها المتبقية.
  - التخصيصات (batch_allocations) لحركات الصرف.
  - العهد الشخصية (custody_out) وإرجاعها (custody_return مع تأثير المعدة)، التلف (damage)، الإرجاع المركزي (central_return).

### 2.2 النقل (Transport) — قناتان

**القناة الأولى: تبادل شبكي مباشر** — `POST /api/sync/exchange`
- يعمل بنمطين:
  - **منسّق (orchestrator):** من جهة إدارية تُرسل `{peerUrl, username, password}`، فتقوم بدور "الوسيط": تجلب تغييراتها، ترسلها للطرف الآخر، تستقبل تغييراته وتطبّقها، ثم تُعيد تقريراً بالاتجاهين (`local` و `peerReport`).
  - **نظير (peer):** عند استقبال طلب من نسخة أخرى، يُتحقق من بيانات الدخول (مسؤول) ثم يُبادل `{nodeId, vector, changes, baseVector, lastVector}`.
- يتطلب اتصالاً شبكياً مباشراً بين النسختين.

**القناة الثانية: حزم ملفات مشفّرة** — `POST /api/sync/export` و `POST /api/sync/import`
- صيغة `DME-SYNC` (مكتبة `lib/backup-format`):
  - توقيع `DME-SYNC\n` + غلاف JSON.
  - التشفير: **AES-256-GCM** بمفتاح مشتق بـ **scrypt** (N=16384, r=8, p=1).
  - سلامة: **SHA-256** للمحتوى + **HMAC-SHA-256** للمصادقة.
  - المحتوى: سطور NDJSON (manifest ثم change لكل تغيير ثم record لكل كيان) مضغوطة بـ gzip.
- التصدير الكامل يرسل كل التغييرات غير المرفوضة؛ والتصدير التفاضلي (delta) يرسل ما بعد `baseVector` إن مُرِّر.
- الاستيراد يعيد التطبيق بإزالة ازدواجية تامة (الاستيراد المكرر = duplicates وليس تعارضات).
- **لا يحتاج أي اتصال شبكي** — الملف يُنقل بأي وسيلة (فلاش، بريد، واتساب، تطبيق ملفات).

### 2.3 التطبيق المادي (Materialization) — `sync-apply-service.ts`

- **تمريران:** تمرير أول للكيانات المرجعية (الأصناف، المواد، المعدات)، ثم تمرير ثانٍ بالترتيب: الحركات → الدفعات → التخصيصات، لضمان وجود المراجع قبل استخدامها.
- **تعيين المعرّفات:** `sync_entity_ids` يربط المعرّف العمومي بالمعرّف المحلي عند كل جهة؛ الوارد الجديد يأخذ معرّفاً محلياً جديداً ويُسجَّل الربط.
- **SAVEPOINT لكل تغيير:** PGlite يُجهِض المعاملة كلها عند أول بيان فاشل؛ لذلك كل تغيير يُغلَّف بـ savepoint، وأي تعارض يُدوَّر له فقط ويُسجَّل كتعارض دون إسقاط بقية الحزمة.
- **إزالة الازدواجية:** بمطابقة `changeId` **أو** `operationId` مع مقارنة قانونية للحمولات (ترتيب مفاتيح موحّد) — فإعادة إرسال نفس الحزمة تُحسب duplicates، ولا تُطبَّق مرتين (لا يتضاعف الرصيد).
- **لاحقة حتمية لرقم السند:** لو أنشأت النسختان `IN-2026-0001` معاً، تُستورد الثانية برقم `IN-2026-0001-<بادئة العقدة>` (مثل `-adb2487a`) — رقم موحّد ومحدد مسبقاً، لا تعارض ولا تكرار.
- **مراجع متسامحة:** `item.categoryId` و `inventory_batch.sourceTransactionId` تُسقط عند عدم تحقق المرجع بدل إفشال التغيير كله (لتقارب البيانات الموجودة قبل المزامنة دون عواصف تعارض).
- **التواريخ:** تحويل تلقائي حسب نوع العمود (timestamptz ← كائن Date، date ← سلسلة) — كان هذا مصدر خلل سابقاً.
- **تطبيع المستخدمين:** المستخدمون لا يُزامَنون بكلمات مرور حقيقية؛ عند وصول مستخدم جديد تُولَّد قيمة عشوائية غير صالحة للدخول (أمان)، والجهات وأسباب الصرف تُنقل كقيم لقطة.

### 2.4 التعارضات وحلّها

تُسجَّل في `sync_conflicts` (تم إصلاح انحراف مخطط سابق: عمود `severity` + ثلاثة جداول مفقودة، مع إصلاح تلقائي عند الإقلاع للقواعد الموجودة). الأنواع:

| الكود | المعنى |
|---|---|
| `UNIQUE_COLLISION` | اصطدام بقيد فريد (مثال: صنف بنفس الاسم موجود عند الطرفين بمعرّفين مختلفين) |
| `OPERATION_PAYLOAD_MISMATCH` | نفس العملية وصلت بحمولة مختلفة |
| `MISSING_REFERENCE` | مرجع غير موجود محلياً (يُعالج تلقائياً في الحالات المتسامحة) |
| `MATERIALIZE_FAILED` | فشل تطبيق غير مصنّف (يُعرض تفصيله في الواجهة) |

الحلّ من صفحة المزامنة: **اعتماد / رفض / تأجيل** — القرار يُسجَّل، والمرفوض يُستبعد من الحزم القادمة (لا عودة للإرسال).

## 3. واجهة المستخدم

صفحة المزامنة (`/sync`) تحتوي الآن:
1. **بطاقة "مزامنة شبكية مباشرة":** عنوان الخادم + مستخدم/كلمة مرور + زر "مزامنة الآن" → يعرض ملخصاً (أرسلنا/استقبلنا/مطبق/مكرر/تعارض) للاتجاهين.
2. **بطاقة "تصدير حزمة مزامنة":** كلمة مرور الحزمة → تنزيل ملف `.dme-sync`.
3. **بطاقة "استيراد حزمة مزامنة":** اختيار الملف + كلمة المرور → تقرير (مطبق/مكرر/تعارض/مرفوض).
4. البطاقات السابقة: معلومات العقدة، الاقتران (pairing)، العقد الموثوقة، Relay، طابور التعارضات.

**أندرويد (وضع الأوفلاين):** أُضيف كاتب الحزم في المتصفح (`dme-sync-browser.ts` — نفس صيغة الخادم تماماً: scrypt + AES-GCM + HMAC + gzip + NDJSON)، ومعالجات `GET /api/sync/node` و `POST /api/sync/export` و `POST /api/sync/import` في `offline-api.ts` مع مطبِّق محلي يعيد بناء الأصناف والمواد والمعدات والحركات والدفعات والعهود، مع نفس قواعد إزالة الازدواجية واللاحقة الحتمية.

## 4. مثال مرحلي: ويندوز ↔ أندرويد

**المرحلة 0 — البداية:** النسخة الأساسية على جهاز ويندوز في المكتب المركزي (كل البيانات موجودة هناك). الهاتف عليه تطبيق أندرويد فارغ (وضع الأوفلاين).

**المرحلة 1 — تصدير من ويندوز:**
المزامنة ← تصدير حزمة مزامنة ← كلمة مرور (مثل `kaskas2026`) ← "تنزيل الحزمة" ← ملف `damascus-sync-2026-08-27.dme-sync`.

**المرحلة 2 — نقل الملف:** انسخه للهاتف بأي وسيلة (كابل USB / بريد / واتساب / Google Drive).

**المرحلة 3 — استيراد على أندرويد:**
المزامنة ← استيراد حزمة مزامنة ← اختر الملف ← أدخل نفس كلمة المرور ← "استيراد وتطبيق". تظهر النتيجة: "استُقبلت N تغييراً: مطبق N، تعارض 0". الآن مخزون الهاتف مطابق للمخزون المركزي (الأصناف، المعدات، الأرصدة، الدفعات، الحركات).

**المرحلة 4 — العمل على الهاتف (بلا إنترنت):** أضف مادة جديدة، سجّل صرفاً أو واردة، حدّث معدّة — كل شيء يعمل محلياً وتُسجَّل التغييرات في سجل الهاتف تلقائياً.

**المرحلة 5 — إعادة التقارب:**
- من الهاتف: تصدير حزمة جديدة → نقلها للويندوز → استيرادها → تظهر تغييرات الهاتف على المكتب المركزي (والعكس بالعكس).
- أو عند توفر شبكة محلية (Wi-Fi): بطاقة "مزامنة شبكية مباشرة" — عنوان جهاز الويندوز (مثل `http://192.168.1.50:8080`) + بيانات مسؤول → "مزامنة الآن" → تقارب فوري بالاتجاهين.

**المرحلة 6 — التعارضات:** لو أُنشئ صنف بنفس الاسم على الجهتين معاً، يظهر في طابور التعارضات؛ اختَر "اعتماد" (يُبقي نسخة الطرف الآخر) أو "رفض" (يُبقي نسختك المحلية) — ويُسجَّل القرار.

## 5. أسئلة مباشرة

### هل المزامنة تلقائية أم يدوية؟
**يدوية حالياً** (زر "مزامنة الآن" / تصدير / استيراد). الالتقاط تلقائي بالكامل (كل عملية كتابة تُسجَّل فوراً)، والتطبيق عند الاستيراد تلقائي، لكن **لحظة النقل** يقررها المستخدم. البنية (متجهات + سجلات) جاهزة لإضافة جدولة تلقائية لاحقاً (مثلاً مزامنة كل 15 دقيقة عند توفر الشبكة) دون تغيير التصميم.

### هل تحتاج النسختان إلى اتصال شبكي بينهما؟
**لا.** قناة حزم الملفات تعمل بدون أي شبكة — يكفي نقل الملف بأي وسيلة. التبادل الشبكي المباشر هو خيار إضافي (أسرع) لكنه ليس شرطاً؛ وحتى في المزامنة الشبكية يكفي أن يصل أحدهما للآخر (لا يحتاجان إنترنت خارجياً، شبكة محلية تكفي).

## 6. نتائج الاختبار (44/44 ✅)

سكربت `docs/tests/api-sync-tests.mjs` على نسختين حيتين (A على 8080، B على 8081) بقاعدة بيانات نظيفة ومُلقّحة:

- تسجيل الدخول وهوية العقدتين (معرّفان مختلفان).
- إنشاء متقاطع: صنف + مادة + معدّة على كل جهة، ثم تبادل #1 → كل جهة تستلم كيانات الأخرى مع **حفظ الأرصدة** (10/5).
- واردة +20 على A و +7 على B، تبادل #2 → **الحركات تعبر بالاتجاهين** (رقم السند بلاحقة حتمية عند التصادم)، الأرصدة تتقارب، الدفعات تُنقل بحالة FEFO.
- حركة معدات +1 وتبادل #3 → الكمية 3 على B.
- تعارض صنف بنفس الاسم (UNIQUE_COLLISION) → يُسجَّل ويُرفض → **لا يعود في الحزم القادمة**.
- تصدير كامل من B واستيراد في A (sync-apply) → **إعادة الاستيراد idempotent** (52 duplicate / 0 تعارض / لا ازدواج رصيد).
- تصدير تفاضلي (delta) بعد التقاط متجه B → استيراد يعمل بدون SYNC_SEQUENCE_GAP.
- إعادة تسمية مادة → تنتشر عبر التبادل.
- حذف ناعم لمادة → ينتشر (isActive=false).

كما أُصلحت خلال التنفيذ أخطاء جوهرية:
- **ترتيب مفاتيح الحمولات** (كان يُصنّف التكرار تعارضاً).
- **تحويل التواريخ** حسب نوع العمود (كان يكسر إدراج الحركات).
- **إجهاض PGlite للمعاملة** عند أول فشل → SAVEPOINT + استرجاع قبل إعادة المحاولة بلاحقة السند.
- **فحص `error.cause`** في تصنيف قيود التفرد (كان يمنع اللاحقة الحتمية).
- **انحراف مخطط** `sync_conflicts.severity` + الجداول الثلاثة المفقودة → إصلاح ذاتي عند الإقلاع.

## 7. القيود المعروفة (المسار القادم)

1. لقطات تغييرات **أندرويد → ويندوز** للعناصر تحمل ملخصاً (وليست لقطة كاملة بعد) — التكميل في النسخة القادمة لجعل الاتجاهين متماثلين بالكامل.
2. المستخدمون لا يُنقلون بكلمات مرور (قيم عشوائية) — أمان مقصود.
3. الجدولة التلقائية غير مفعّلة — يدوي حتى الآن.
4. `pnpm-workspace.yaml` فيه تعديل محلي (مسار) غير مرغوب برفعه — يُستثنى من الالتزامات.
