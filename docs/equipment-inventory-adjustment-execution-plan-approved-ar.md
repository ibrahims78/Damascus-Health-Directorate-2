## 1. الملخص التنفيذي

### 1.1 المشكلة (مؤكدة بالكود)

| المسار | السلوك الحالي | الدليل في الكود |
|---|---|---|
| المواد | الرصيد يتغير عبر `POST /api/transactions/adjust` → حركة `adjust` موثقة بسند | `adjustment-form.tsx` + `createAdjustment` |
| التجهيزات | الرصيد يتغير عبر `PUT /api/equipment/:id` (حقل `quantity`) → تدقيق `update` فقط، بلا سند حركة | `equipment-form.tsx:55` + مسار `PUT` |

**سبب الاختلاف:** حصر تاريخي غير مكتمل — دالة `createAdjustment` في
`inventory-movement-service.ts:964` ترفض التجهيزات برمز `ITEM_ADJUSTMENT_ONLY`، بينما
البنية التحتية الكاملة لحركات التجهيز (قفل `FOR UPDATE`، حساب العهد المتاح، قاعدة
الرقم التسلسلي، حقول `equipmentId` في `transactions`) موجودة وتُستخدم لحركات أخرى
(إدخال، عهدة، تلف، مرتجع). `[م]`

### 1.2 القرار المعماري (موصى به)

تغيير كمية التجهيز = **حركة مخزنية موثقة** تمر عبر الخدمة المركزية
`createInventoryMovement`، لا تعديل بيانات صامت. التفاصيل في القسم 2.

## 2. خط الأساس المثبت (أُعيد التحقق منه بالكود بتاريخ 26-08-2026)

| المجال | الوضع المؤكد | الأثر |
|---|---|---|
| `POST /api/transactions/adjust` | موجود، يرفض التجهيز بـ `ITEM_ADJUSTMENT_ONLY` | نقطة التوسعة الرسمية |
| `createInventoryMovement` | معاملة ذرية + `ensureNodeIdentity` + `reserveOriginSequence` + `lockDocumentNumber` | كل تسوية تمر منها |
| `lockEquipment` | `SELECT ... FOR UPDATE` موجود (سطر 233) | يُعاد استخدامه |
| حساب العهد المفتوحة | `calculateEquipmentAvailable` موجود (سطر 28) | يُدمج في معاملة التسوية |
| قاعدة الرقم التسلسلي | `SERIAL_EQUIPMENT_QUANTITY_INVALID` موجود (سطر 627) لحركات أخرى | يُعاد استخدامه/توسيعه |
| جدول `transactions` | يدعم `itemType='equipment'` + `equipmentId` + `operationId` + CHECKs | كافٍ للحركة نفسها؛ اللقطات تحتاج قراراً (3.1) |
| جدول `transactions` — اللقطات | **لا يحتوي لقطات للتجهيز** (الاسم/الموديل/الرقم التسلسلي/الحالة) | **قرار 3.1** |
| الطباعة | مسار `/print/:id` موجود وسند A4 للمواد | يُعاد استخدامه مع توسيع لتجهيز |
| التدقيق | `audit_log` مع `auditLogStrict` للفشل | يُربط برقم الحركة |
| المزامنة | `operationId` + `originSequence` + outbox/inbox | حماية idempotency جاهزة |
| الواجهة | `adjustment-form.tsx` مواد فقط؛ `equipment-form.tsx` يعرض/يرسل `quantity` | فصل + واجهة جديدة |
| OpenAPI | `lib/api-spec/openapi.yaml` (78 مساراً) + توليد Orval | **تحديث إلزامي أولاً** `[م]` |

## 4. العقد النهائي (طلب + استجابة + أكواد) `[م]`

### 4.1 الطلب

```text
POST /api/transactions/adjust
{
  itemType: "item" | "equipment",
  itemId?: number,        // إلزامي إذا itemType = item
  equipmentId?: number,   // إلزامي إذا itemType = equipment
  newStock: number,       // عدد صحيح غير سالب، وفق سياسة 3.6
  documentDate: "YYYY-MM-DD",
  reason: string,         // إلزامي، ≥ 5 أحرف بعد الفراغات
  notes?: string
}
```

قواعد صارمة:
- `itemId` XOR `equipmentId` حسب `itemType` — رفض بـ `ENTITY_TYPE_MISMATCH`.
- الخادم يحسب `delta` من الرصيد **المقفول**؛ أي `delta` مرسل من العميل يُتجاهل.
- `documentNumber` يولَّد تلقائياً عبر `lockDocumentNumber` الموجود (نفس آلية الحركات الحالية) — لا يقبل من العميل. `[م]`

### 4.2 الاستجابة

```text
201 Created
{
  id, operationId, type: "adjust", itemType,
  itemId | equipmentId,
  quantity: abs(delta),
  documentNumber, documentDate,
  reason, notes,
  details: {                 // من عمود details (قرار 3.1)
    previousStock, newStock, delta, deltaType: "increase"|"decrease",
    equipmentNameSnap?, equipmentModelSnap?,
    equipmentSerialSnap?, equipmentConditionSnap?
  },
  createdAt
}
```

### 4.3 جدول أكواد الخطأ النهائي (رسائل عربية معتمدة) `[م]`

| الكود | الحالة | الرسالة العربية |
|---|---|---|
| `ENTITY_TYPE_MISMATCH` | 400 | مرجع المادة/التجهيز لا يطابق النوع المحدد |
| `ITEM_NOT_FOUND` | 404 | المادة غير موجودة |
| `EQUIPMENT_NOT_FOUND` | 404 | التجهيز غير موجود |
| `INVALID_STOCK` | 400 | الرصيد الجديد غير صالح |
| `NO_STOCK_CHANGE` | 400 | الرصيد الجديد مطابق للرصيد الحالي |
| `EQUIPMENT_CUSTODY_BALANCE` | 409 | لا يمكن إنقاص الرصيد عن الكمية المفتوحة على العهد |
| `SERIAL_EQUIPMENT_ADJUSTMENT_BLOCKED` | 409 | التجهيز المسلسَل يُعالَج عبر مسار الفقد/الشطب أو تغيير الحالة |
| `REQUIRED_FIELD` | 400 | السبب أو التاريخ المطلوب ناقص |
| `REASON_TOO_SHORT` | 400 | السبب قصير جداً (5 أحرف على الأقل) |
| `INVALID_DOCUMENT_DATE` | 400 | تاريخ الجرد غير صالح |
| `LEGACY_EQUIPMENT_QUANTITY_REJECTED` | 409 | تعديل كمية التجهيز من إصدار قديم غير مقبول؛ استخدم تسوية الجرد (قرار 3.2) |
| `INTERNAL_MOVEMENT_ERROR` | 500 | خطأ داخلي في تسجيل الحركة |

> الأكواد الموجودة أصلاً (`INVALID_STOCK`, `NO_STOCK_CHANGE`, `REQUIRED_FIELD`, `ITEM_NOT_FOUND`) تُعاد استخدامها كما هي — لا تكسر توافق العملاء الحاليين للمواد.

## 5. قواعد الرصيد النهائية (لا تُكسر)

1. `equipment.quantity` = إجمالي الوحدات التشغيلية المسجلة.
2. المتاح للعهدة = الإجمالي − العهد المفتوحة.
3. تسليم العهدة لا يخفض الإجمالي؛ الإرجاع الجيد لا يرفعه.
4. التلف والمرتجع المركزي يخفضان عبر حركتيهما المستقلتين.
5. **الرصيد الجديد = عداد المستودع + العهد المفتوحة** (قرار 3.4).
6. الرصيد الجديد ≥ العهد المفتوحة (قرار 3.5) — إلا في حالات التصحيح الموثقة التي تعالج العهد نفسها.
7. التجهيز المسلسَل: لا تسوية (قرار 3.3).
8. الصفر: وفق سياسة 3.6.
9. الفشل في أي تحقق = إلغاء كامل للحركة مع أثر `movement_failed` في التدقيق.
10. لا حذف؛ التصحيح بحركة جديدة (قرار 3.10).

  - رفض المسلسَل (قرار 3.3).
  - حساب `openCustody` داخل المعاملة عبر `calculateEquipmentAvailable` أو استعلام مباشر `SUM(quantity - returned)`.
  - التحقق `newStock >= openCustody` وإلا `EQUIPMENT_CUSTODY_BALANCE`.
  - `delta = newStock - equipment.quantity` (من المقفول)؛ `delta===0` → `NO_STOCK_CHANGE`.
  - إدراج `transactions` بنوع `adjust` + `quantity=abs(delta)` + `details` (لقطة + قبل/بعد).
  - `UPDATE equipment SET quantity = newStock`.
- كتابة `movement_created` بالتفاصيل، و`movement_failed` خارج المعاملة عند الفشل (السلوك الحالي).

**المرحلة 3 — فصل الحقل** (قرار حاسم): `[م]`
- الواجهة: إزالة `quantity` من وضع التحرير، إبقاؤه في الإضافة فقط.
- الخادم: `PUT /api/equipment/:id` **يرفض** وجود `quantity` مختلف عن القيمة الحالية برسالة واضحة (لا يتجاهل بصمت). السماح بإرسال نفس القيمة (idempotent) لتفادي كسر عملاء قديمين يرسلون القيمة كاملة — **استثناء مقصود، موثق في الاختبارات**.

**المرحلة 8 — المزامنة** (المهام المضافة): `[م]`
- رفض تغييرات المزامنة التي تعدّل `equipment.quantity` خارج حركة (قرار 3.2) بكود `LEGACY_EQUIPMENT_QUANTITY_REJECTED`.
- اختبار إعادة الإرسال عبر `operationId` (idempotency موجود — يُختبر صراحةً لحركة adjust).
- تعارض تسويتين لنفس التجهيز: الأحدث زمنياً يفوز ويُسجل التعارض في `sync_conflicts` — لا استبدال صامت.

**المرحلة 9 — إطار الاختبار** (إضافة إلزامية): `[م]`
- **الوحدة:** Vitest (متوافق مع TS، خفيف) لـ `inventory-movement-core` + دوال حساب التسوية الجديدة.
- **التكامل/API:** سكربتات phase الموجودة (تُوسَّع بحالات adjust الجديدة) — لا ننشئ إطاراً موازياً.
- **قاعدة البيانات:** قيود + معاملة + تزامن (اختبار `FOR UPDATE` **على PostgreSQL فقط** — PGlite وIndexedDB تنفيذهما مسلسل فلا فائدة).
- **الواجهة:** اختبار يدوي موثق + اختبارات مخطط Zod للنموذج.
- **الأمان:** فحص عدم تسرب أسرار إلى Git/مخرجات البناء.
